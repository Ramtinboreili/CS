2. Backup and recovery
@@ b7-2|body#19
<b>Full / incremental / differential:</b> complete, only changes since the last backup, changes since the last full backup.
@@ b7-2|body#20
<b>Logical (pg_dump) versus physical (copying files + WAL):</b> physical is faster for large volumes.
@@ b7-2|body#21
<b>Point-in-time recovery (PITR):</b> a base backup + continuous WAL archiving ⇒ return to any moment (for example one minute before an accidental DELETE).
@@ b7-2|body#22
<b>RPO</b> (recovery point objective): the maximum data that may be lost (time). <b>RTO</b> (recovery time objective): the maximum acceptable downtime.
@@ b7-2|body#23
A backup whose <b>restore has not been tested</b> is not a backup. The 3-2-1 rule: 3 copies, 2 media, 1 off-site.
@@ b7-2|body#24
3. Connection pooling
@@ b7-2|body#25
Creating a database connection is expensive (TCP, TLS, authentication, and in PostgreSQL a new process). A <b>connection pool</b> keeps some connections open and lends them between requests (HikariCP, PgBouncer). Estimate a suitable size with <b>Little's law</b>: $L=\lambda W$ (concurrency = arrival rate × time held). A bigger pool is not better: the database's CPU/disk is limited and many connections only create contention and memory use.

1. Storage hierarchy and the page
@@ b8-1|body#1
A DBMS stores and moves data on disk in fixed blocks called <b>pages</b> (8 KB in PostgreSQL, 16 KB in InnoDB). The I/O unit is the page, not the row. Each page has an identifier (file, page number). A table is usually a <b>heap file</b> of pages and indexes are other files.
@@ b8-1|body#2
The slotted page
@@ b8-1|body#3
Rows have variable length. In the slotted-page structure: a <b>header</b> (id, the LSN of the last change, slot count, free space), a <b>slot array</b> from the start that points to each row, and the <b>rows</b> growing from the end of the page toward the middle; the free space is between them. The row identifier is the <b>RID = (page no., slot no.)</b>; moving a row within a page only changes the slot and the RID stays fixed. Very large rows (TOAST/overflow) are stored separately.
@@ b8-1|body#4
2. The buffer pool
@@ b8-1|body#5
The <b>buffer pool</b> is a region of RAM that keeps copies of recent pages. A page request: if it is in the pool (<b>hit</b>) it is returned directly; otherwise (<b>miss</b>) it is read from disk and, if there is no room, a <b>victim</b> page is chosen; if it is dirty (changed but not yet written to disk) it must be written to disk before removal. A page in use is <b>pinned</b> and not evicted.
@@ b8-1|body#6
The crucial effect: RAM access ≈ 100 ns, SSD ≈ 100 µs (1000×), HDD ≈ 10 ms (100,000×). With hit ratio $h$ the average access time is $h\cdot t_{RAM}+(1-h)\cdot t_{disk}$; so 99% versus 90% hits means about 10× fewer misses.
@@ b8-1|body#7
<b>Replacement policies:</b> LRU (least recently used), clock (a cheap LRU approximation), LRU-K / 2Q / ARC which are more robust. The problem with plain LRU: <b>sequential flooding</b> — one big full table scan flushes out all the "hot" pages. Remedies: a small ring buffer for large scans (PostgreSQL) or a "young/old" region (InnoDB midpoint insertion).
@@ b8-1|body#8
Buffer-pool simulator with LRU
@@ b8-1|body#9
Note: DBMSs usually have a dedicated buffer pool and bypass the operating-system file cache (<code>O_DIRECT</code>) because they know better which pages are valuable and must control the order of writes (WAL).

2. Write-ahead logging
@@ b8-2|body#13
<b>The WAL rule:</b> (1) each change's log record must be durable <u>before</u> the changed page is written to disk (guarantees undo); (2) all of a transaction's log records must be durable <u>before</u> the COMMIT reply (guarantees redo/durability). Writing the log is <b>sequential (append-only)</b> and much faster than random page writes (made durable with <code>fsync</code>; <i>group commit</i> gathers several commits into one fsync).
@@ b8-2|body#14
Each log record has a sequence number, the <b>LSN</b>, and contains: transaction id, page, <b>before-image</b> (for undo) and <b>after-image</b> (for redo), or a physiological form. Each page keeps the LSN of its last change so that redo is <b>idempotent</b>.
@@ b8-2|body#15
3. Checkpoints
@@ b8-2|body#16
Without a limit, recovery would have to replay the whole log from the beginning. A <b>checkpoint</b> writes dirty pages to disk (or records in the log a list of them and of the active transactions) so that recovery starts only from the last checkpoint. The trade-off: frequent checkpoints ⇒ fast recovery but more background I/O; rare ⇒ the opposite. (A <i>fuzzy checkpoint</i> is taken without stopping transactions.)
@@ b8-2|body#17
4. Crash recovery (the ARIES pattern)
@@ b8-2|body#18
<b>Analysis:</b> the log is read from the last checkpoint to identify the "winner" transactions (committed), the "loser" ones (active at the crash) and the possibly dirty pages.
@@ b8-2|body#19
<b>Redo:</b> <i>history is repeated</i> — all logged changes (even of loser transactions) are re-applied (if the page's LSN is lower than the record's LSN). The exact state at the moment of the crash is rebuilt.
@@ b8-2|body#20
<b>Undo:</b> the changes of loser transactions are reverted with the before-images, from last to first (each undo itself writes a compensation log record, CLR, so that a crash during recovery is also tolerable).
