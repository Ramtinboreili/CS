1. What is an algorithm?
@@ a1-1|body#1
<b>An algorithm</b> is a finite, precisely defined sequence of steps that turns an input into a desired output. To count as an "algorithm" a method needs five properties: <b>input</b>, <b>output</b>, <b>definiteness</b> (every step unambiguous), <b>finiteness</b> (it ends after a finite number of steps) and <b>effectiveness</b> (every step can be carried out with real resources).
@@ a1-1|body#2
Two different questions must be asked about any algorithm: (1) <b>Is it correct?</b> Does it give the right output for every valid input? (2) <b>Is it efficient?</b> How much time and memory does it need, and how does that grow as the input grows? This lesson is about the second question. Correctness is usually proved by induction or by a loop invariant.
@@ a1-1|body#3
2. Why "analysis" and not just timing?
@@ a1-1|body#4
Measured running time depends on the hardware, the language, the compiler and the test inputs. In theoretical analysis we use the <b>RAM model</b>: every basic operation (addition, comparison, reading/writing one memory cell) has unit cost, and we ask how the number of these operations depends on the <b>input size</b> $n$. We call that function $T(n)$. The goal is to predict the <b>growth behaviour</b>, not the exact time in seconds.

3. Space complexity
@@ a1-1|body#12
<b>Space complexity</b> is the amount of memory the algorithm uses beyond the input (<i>auxiliary space</i>). The memory of the recursive call stack counts too: a recursive function of depth $n$ needs $O(n)$ memory even if it has no helper variables. There is usually a trade-off between time and memory; for example a hash table gives faster lookup in exchange for more memory.

4. Asymptotic notation
@@ a1-1|body#14
Let $f,g:\mathbb{N}\to\mathbb{R}_{\ge0}$.
@@ a1-1|body#15

$$f(n)=O(g(n))\iff \exists\,c>0,\,n_0:\ \forall n\ge n_0,\ f(n)\le c\,g(n)$$
$$f(n)=\Omega(g(n))\iff \exists\,c>0,\,n_0:\ \forall n\ge n_0,\ f(n)\ge c\,g(n)$$
$$f(n)=\Theta(g(n))\iff f=O(g)\ \text{and}\ f=\Omega(g)$$

@@ a1-1|body#16
<b>Proof example:</b> we show $3n^2+5n+2=\Theta(n^2)$. For $n\ge1$ we have $3n^2\le 3n^2+5n+2\le 3n^2+5n^2+2n^2=10n^2$. So with $c_1=3$, $c_2=10$ and $n_0=1$ both sides hold.
@@ a1-1|body#17
<b class="t">Careful: Big-O is not the same as "worst case" or "running time"</b>$O(g)$ is only an <b>upper bound on a function</b> and can be applied separately to the best, average or worst case. The sentence "this algorithm is $O(n^2)$" does not by itself say what the exact time is; it only says its growth is no more than $n^2$. When we want a tight bound we use $\Theta$.
@@ a1-1|body#18
5. Best, average and worst case
@@ a1-1|body#19
For inputs of the same size $n$ the running time can differ. The <b>best case</b> is the minimum, the <b>worst case</b> the maximum and the <b>average case</b> the expected time under an assumed distribution over inputs. In linear search: the best case is 1 comparison ($\Theta(1)$), the worst case $n$ comparisons and the average (assuming a uniformly random target position) $\frac{n+1}{2}$.

7. Limits of asymptotic analysis
@@ a1-1|body#31
For small $n$ or large constants, an algorithm that is "worse" in order can be faster (for example insertion sort on a small array beats merge sort; that is why real sort implementations are hybrids). Asymptotic analysis also does not model the effect of the cache, I/O and parallelism.

The problem
@@ a1-2|body#1
Sometimes an operation is cheap most of the time and very expensive rarely. If we count only the worst case of that single operation we are too pessimistic. <b>Amortized analysis</b> measures the total cost of a <b>sequence</b> of $n$ operations in the <b>worst sequence</b> and divides by $n$. It is a deterministic guarantee for the sequence of operations, not a probabilistic analysis.
@@ a1-2|body#2
Main example: the dynamic array
@@ a1-2|body#3
When the array is full we build a new array of double the capacity and copy all the elements (cost $\Theta(k)$ when copying $k$ elements). An ordinary push is $\Theta(1)$.
@@ a1-2|body#4
The aggregate method
@@ a1-2|body#5

@@ a1-2|body#6
So the total cost is $\le n+2n=3n$ and the amortized cost of each push is below 3, i.e. $O(1)$.
@@ a1-2|body#7
The accounting method
@@ a1-2|body#8
We charge each push an amortized cost of 3 "coins": 1 coin for the insertion itself, 1 coin for copying this same element at the next growth, and 1 coin as savings for copying one of the older half's elements. When a growth happens, the saved coins pay for the copying and the balance never goes negative.
@@ a1-2|body#9
The potential method
@@ a1-2|body#10
Define the potential function $\Phi=2\cdot\text{size}-\text{capacity}$. The amortized cost of operation $i$ is $\hat c_i=c_i+\Phi_i-\Phi_{i-1}$. For a push without growth: $\hat c=1+2=3$. For a push with growth (with $k$ old elements): $c=k+1$ and the potential goes from $2k-k=k$ to $2(k+1)-2k=2$, so $\hat c=(k+1)+(2-k)=3$. Both cases give a constant.
@@ a1-2|body#11
Dynamic-array simulator: doubling versus a fixed increase
@@ a1-2|body#12
If the capacity grows by adding a fixed amount $c$ instead of multiplying by a constant factor, the number of copies is $\Theta(n/c)$ and the total copying is $\Theta(n^2/c)$; so the amortized cost is $\Theta(n)$, not $O(1)$ — which is why geometric growth (×1.5 or ×2) is the standard.

Why is a growth factor of 1.5 preferred over 2 in some implementations? (Hint: reusing freed memory)
@@ a1-2|ex:3:a#0
With factor 2 the sum of all previous block sizes is always less than the new block ($1+2+\dots+2^{k-1}<2^k$), so the allocator can never combine the previously freed blocks for the next growth and reuse them.
