1. The array
@@ a2-1|body#1
An array is a sequence of equally sized elements stored in a <b>contiguous block of memory</b>. If the start address is $base$ and each element has size $s$, the address of element $i$ is $base+i\cdot s$: one multiplication and one addition, independent of $n$. This is the reason for <b>$O(1)$ random access</b>.
@@ a2-1|body#2
But inserting or deleting in the middle of an array must shift the later elements: $O(n)$. A static array's size is fixed at creation. A <b>dynamic array</b> (like <code>list</code> in Python, <code>vector</code> in C++ and <code>ArrayList</code> in Java) makes appending at the end amortized $O(1)$ through geometric capacity growth (previous lesson).

2. The linked list
@@ a2-1|body#4

4. Cache locality: why the array wins in practice
@@ a2-1|body#27
The processor reads data in 64-byte <b>cache lines</b>. Scanning an array gets neighbouring elements in one cache line (spatial locality) and the CPU prefetcher reads ahead. Linked-list nodes are scattered and every hop to the next node may be a cache miss (hundreds of cycles). For this reason, in many applications even middle insertions into a dynamic array are faster than in a linked list unless $n$ is very large.

ADT and implementation
@@ a2-2|body#1
An <b>abstract data type (ADT)</b> specifies only the operations and behaviour, not how it is stored. Stack, queue and deque are three ADTs, each implementable with a dynamic array, a circular array or a linked list.
@@ a2-2|body#2
Stack — "last in, first out" (LIFO)
@@ a2-2|body#3
Operations: <code>push</code>, <code>pop</code>, <code>peek</code>, <code>isEmpty</code>; all $O(1)$ (amortized in a dynamic array). Like a pile of stacked dishes. Uses: the language <b>call stack</b>, undo/redo, evaluating postfix expressions, matching parentheses and non-recursive DFS.
@@ a2-2|body#4
O(n) time, O(n) memory
@@ a2-2|body#5
Queue — "first in, first out" (FIFO)
@@ a2-2|body#6
Operations: <code>enqueue</code> (at the end), <code>dequeue</code> (from the front). If we build a queue with a plain array and remove from the front, the cost is $O(n)$; the solution is a <b>circular buffer</b> with two indices <code>head</code> and <code>tail</code> and modular arithmetic. Uses: BFS, process scheduling (round robin), network buffers, message queues (Kafka/RabbitMQ).
@@ a2-2|body#7
Deque — the double-ended queue
@@ a2-2|body#8
Insert and delete at both ends in $O(1)$. An important pattern is the <b>monotonic deque</b> for "maximum in a sliding window" in $O(n)$: we keep indices whose values decrease from front to back; an element smaller than the new one is removed from the back because it can never be the answer.

Show how to implement a queue with two stacks and give the amortized cost of each operation.
@@ a2-2|ex:4:a#0
Two stacks, in and out. enqueue: push onto in ($O(1)$). dequeue: if out is empty, pop all elements of in one by one and push them onto out (the order reverses and the front of the queue ends up on top of out), then pop from out. The idea
@@ a2-3|body#1
A <b>hash table</b> is a mapping from keys to values that performs lookup/insert/delete in $O(1)$ on average by converting the key into an array index. A <b>hash function</b> $h:\text{Keys}\to\{0,\dots,m-1\}$ maps a key to one of $m$ slots. Since the key domain is much larger than $m$, by the <b>pigeonhole principle</b> collisions are unavoidable.
@@ a2-3|body#2
A good hash function
@@ a2-3|body#3
<b>Deterministic:</b> a key always gives the same output.
@@ a2-3|body#4
<b>Uniform distribution:</b> it spreads keys roughly equally over the slots.
@@ a2-3|body#5
<b>Fast:</b> cheap to compute.
@@ a2-3|body#6
String example: $h(s)=\left(\sum_{i} s_i\cdot 31^{\,len-1-i}\right)\bmod m$ (a polynomial with a prime base). Note: a hash-table hash function differs from a <i>cryptographic</i> hash function (SHA-256); the former needs speed and good spreading, the latter resistance to deliberate collisions.
@@ a2-3|body#7
Resolving collisions
@@ a2-3|body#8
1. Separate chaining
@@ a2-3|body#9
Each slot is a list (chain) of the keys that land in it. The search cost is $\Theta(1+\alpha)$ where $\alpha=n/m$ is the <b>load factor</b>. If the hash is "simple uniform" and $\alpha=O(1)$ the average time is $O(1)$; but in the worst case (all keys in one slot) it becomes $O(n)$ (Java 8+ turns long chains into balanced trees).
@@ a2-3|body#10
2. Open addressing
@@ a2-3|body#11
All keys live inside the array itself. On a collision a probe sequence looks for an empty slot: <b>linear probing</b> ($h+i$), <b>quadratic</b> ($h+i^2$) and <b>double hashing</b> ($h_1+i\,h_2$). Linear probing is cache-friendly but suffers <b>primary clustering</b>: contiguous clusters grow and search time explodes as $\alpha$ approaches 1 (on average ≈ $\frac12(1+\frac1{(1-\alpha)^2})$ for an unsuccessful search). Deletion must use a <b>tombstone</b>, otherwise the probe chain of other keys breaks.
@@ a2-3|body#12
Hash-table simulator (chaining and linear probing)
@@ a2-3|body#13
Rehash and amortized analysis
@@ a2-3|body#14
When $\alpha$ exceeds a threshold (say 0.75 in Java, 2/3 in Python), a table of double the size is built and all keys are rehashed (because $m$ changed). This operation costs $O(n)$ but, like the dynamic array, it adds up to amortized $O(1)$ per insertion.
@@ a2-3|body#15
Applications and limits
@@ a2-3|body#16
Dictionary/map (<code>dict</code>, <code>HashMap</code>), set (<code>set</code>), frequency counting, removing duplicates, memoization, caches.
@@ a2-3|body#17
In databases: the <b>hash join</b> and the <b>hash index</b> (for equality, but not ranges).
@@ a2-3|body#18
Limit: key order is not preserved, range/min search is impossible, and keys must be <i>immutable</i> with consistent <code>equals/hash</code>.

@@ a2-3|ex:4:a#0
