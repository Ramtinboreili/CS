3. Functional dependencies (FD)
@@ b4-1|body#14
$X\to Y$ means any two rows with the same $X$ value have the same $Y$ value (for example <code>student_id → student_name</code>). FDs come from the "meaning of the data", not from the current data. The <b>attribute closure</b> $X^+$ is all the attributes inferable from $X$ (by repeatedly expanding with the FDs). $X$ is a superkey if $X^+$ is all the attributes; if it is also minimal, a candidate key.
@@ b4-1|body#15
<b>Armstrong's axioms:</b> reflexivity ($Y\subseteq X\Rightarrow X\to Y$), augmentation ($X\to Y\Rightarrow XZ\to YZ$) and transitivity ($X\to Y,\ Y\to Z\Rightarrow X\to Z$), from which union, decomposition and so on follow.

1. Why an index?
@@ b5-1|body#1
Without an index, finding the rows of <code>WHERE email = ?</code> needs a <b>full scan</b> of the table: $\Theta(n)$ pages are read. An <b>index</b> is a separate auxiliary structure that keeps keys sorted and points to the row location, like a book's back-of-book index. An index is not free: it takes <b>memory</b> and <b>every INSERT/UPDATE/DELETE</b> must update it too.
@@ b5-1|body#2
2. The real cost: pages, not rows
@@ b5-1|body#3
A disk (and an SSD) reads data in fixed <b>pages</b> (usually 4–16 KB). The dominant cost of a query is the number of pages that must be brought into memory, not the number of comparisons. A balanced binary BST with $10^8$ keys has ≈ 27 levels and each level may be a random read. If each node is a whole page with hundreds of keys (<b>fan-out</b> $F\approx200$), the height $\log_F n\approx4$!
@@ b5-1|body#4
Height of a binary BST versus a B+Tree
@@ b5-1|body#5
3. B-trees and B+trees
@@ b5-1|body#6
A <b>B-tree (of order $m$)</b> is a balanced multiway search tree: each node has at most $m$ children (and $m-1$ keys), each internal (non-root) node at least $\lceil m/2\rceil$ children, and <b>all leaves are at the same depth</b> (unlike a BST it grows not from the "bottom" but by splits and root growth). Height $O(\log_{m/2}n)$.
@@ b5-1|body#7
A <b>B+tree</b> (the common type in DBMSs) differs in two ways: (1) <b>data/row pointers live only in the leaves</b> and internal nodes hold only "separator keys", so the fan-out is higher and the height lower; (2) <b>the leaves are linked in a list</b>, so a range query (<code>BETWEEN</code>, <code>ORDER BY</code>) after finding the start is done by walking the leaves linearly.
@@ b5-1|body#8
Interactive B+tree: insert, split, search and range scan
@@ b5-1|body#9
Operations
@@ b5-1|body#10
<b>Search:</b> from the root, at each node choose the right child by comparing the key (binary search within the node); $h$ pages are read: $O(\log_F n)$.
@@ b5-1|body#11
<b>Insert:</b> find the right leaf and insert the key. If the leaf overflows (beyond capacity), <b>split</b>: half of the keys move to a new node and a separator key is added to the parent (this may cascade upward and eventually create a new root and increase the height). Result: the tree is always balanced.
@@ b5-1|body#12
<b>Delete:</b> after deletion, if a node falls below the minimum, <b>redistribute</b> (borrow from a neighbour) or <b>merge</b>. (Real implementations sometimes delay merging.)

Why can using a random UUID as the primary key in a table with a clustered index (like InnoDB) hurt write performance?
@@ b5-1|ex:4:a#0
In a clustered index data is stored in PK order. A random key sends each insert to a random page of the tree; that page must be read from disk and (since it is full) split, and pages end up half empty. Result: random I/O, many cache misses, fragmentation and more space. Also, secondary indexes repeat the PK in their leaves and a 16-byte key makes them larger. An increasing key (or a time-ordered UUID) concentrates inserts at the end of the tree.
