1. The composite (multi-column) index
@@ b5-2|body#1
An index on $(a,b,c)$ is sorted <i>lexicographically</i>: first by $a$, then within each $a$ by $b$, and so on. So it can seek only for <b>left prefixes</b> ($a$ or $a,b$ or $a,b,c$). Equality conditions on the first columns and at most <i>one</i> range condition (on the last usable column) are the best case; columns after the range condition are only filtered. The rule of thumb for column order: <b>equalities first, then the range, then ORDER BY</b>, and the column with higher selectivity usually earlier.

2. The covering index and index-only scan
@@ b5-2|body#4
If all the columns a query needs are in the index itself (for example <code>CREATE INDEX ON t(a, b) INCLUDE (c)</code>), the DBMS does not need to go to the table pages: an <b>index-only scan</b>. This removes the second random access but makes the index bigger.

4. Storage engines
@@ b5-2|body#25
The storage engine determines how data is kept and accessed (MySQL has several selectable engines). Two main families of storage structure:
@@ b5-2|body#26
<b>B+tree-based (in-place update):</b> InnoDB, PostgreSQL (heap + B-tree), SQL Server. Fast, predictable reads; random writes and fragmentation.
@@ b5-2|body#27
<b>LSM tree (log-structured merge):</b> RocksDB, Cassandra, LevelDB. Writes go first to the memtable and the WAL, then are flushed as immutable sorted files (SSTables) on disk and <b>compacted</b> in the background. Fast sequential writes; reads may touch several files (mitigated with Bloom filters) and there is write amplification from compaction.
@@ b5-2|body#28
<b>Row versus columnar storage:</b> columnar (Parquet, ClickHouse, Redshift) for aggregating a few columns over billions of rows; row storage for fetching a whole row and OLTP writes.

@@ b6-1|body#19

@@ b6-1|body#20

1. Pessimistic concurrency control: locking
@@ b6-2|body#1
A <b>shared lock (S)</b> for reading (several concurrent readers) and an <b>exclusive lock (X)</b> for writing. Compatibility matrix: S is compatible with S; X with nothing. Lock scope: row, page, table (<i>lock granularity</i> — finer locks give more concurrency but more overhead).
@@ b6-2|body#2
<b>Two-phase locking (2PL):</b> each transaction first only acquires locks (growing phase) and after its first release can no longer acquire any (shrinking phase). 2PL guarantees <b>serializability</b>. <b>Strict 2PL</b> keeps X locks until the end of the transaction to prevent cascading aborts and dirty reads (common in practice).

2. Deadlock
@@ b6-2|body#6
When several transactions wait for each other's locks in a cycle. Coffman's four necessary conditions: mutual exclusion, hold and wait, no preemption, circular wait. <b>Detection:</b> build a <i>wait-for graph</i> and look for a cycle; the DBMS picks one transaction as a victim and rolls it back. <b>Prevention:</b> a fixed lock order, short transactions, acquiring all resources at once, timeouts, or timestamp-based wait-die/wound-wait schemes.

3. MVCC — multi-version concurrency control
@@ b6-2|body#9
Instead of preventing reads during writes, the DBMS keeps <b>several versions</b> of each row. Each version is labelled with the creating transaction (<code>xmin</code>) and the deleting transaction (<code>xmax</code>). Each transaction takes a <b>snapshot</b> and sees only the versions committed up to that moment. Result: <b>readers do not block writers and vice versa.</b> Cost: memory for old versions and their <b>cleanup</b> (VACUUM in PostgreSQL; undo log and purge in InnoDB), and write–write conflicts still need locks.

1. Scalability
@@ b7-1|body#1
<b>Vertical scaling (scale-up)</b> a stronger machine; simple but with a ceiling. <b>Horizontal scaling (scale-out)</b> adding machines; complex (data distribution, consistency) but almost unlimited. 2. Replication
@@ b7-1|body#3
<b>Leader–follower (primary–replica):</b> all writes go to the leader and the log is sent to the followers; reads can go to the followers.
@@ b7-1|body#4
<b>Synchronous:</b> the leader waits for the replica's acknowledgement ⇒ stronger durability and consistency, more latency and lower availability. <b>Asynchronous:</b> fast but with <b>replication lag</b> (reading a stale value, losing the latest writes when the leader fails). <b>Semi-sync:</b> at least one synchronous replica.
@@ b7-1|body#5
<b>Multi-leader / leaderless (Dynamo, Cassandra):</b> writes to several nodes, needing conflict resolution (last-write-wins, CRDTs, vector clocks) and quorums: $R+W>N$ to read the latest write.

3. Partitioning and sharding
@@ b7-1|body#8
<b>Partitioning:</b> splitting a big table into smaller pieces (usually on one server) for manageability and query pruning: <i>range</i> (by date), <i>list</i>, <i>hash</i>. <b>Sharding:</b> horizontal partitioning across several independent servers; the shard key decides where each row goes. A bad key choice ⇒ a <b>hot shard</b> (for example a timestamp that sends all writes to the last shard). Cross-shard queries, joins and distributed transactions are expensive.
@@ b7-1|body#9
With <code>hash(key) mod N</code>, changing $N$ moves almost all keys. <b>Consistent hashing</b> places keys and nodes on a hash ring and each key goes to the first node clockwise; when a node is added/removed only a fraction $\approx1/N$ of the keys moves. Virtual nodes (vnodes) even out the distribution.

4. The CAP theorem and consistency models
@@ b7-1|body#12
In a distributed system during a network <b>partition</b> (which is unavoidable) you must choose between <b>consistency</b> (every read sees the latest write — linearizability) and <b>availability</b> (every request gets a non-error response). "CAP" is often wrongly stated as "choose 2 of 3"; more precisely: <i>if a partition occurs, either C or A</i>. <b>PACELC</b> adds: even without a partition (else) there is a trade-off between <b>latency</b> and <b>consistency</b>.
