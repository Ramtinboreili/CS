1. The database and the DBMS
@@ b1-1|body#1
A <b>database</b> is an organized, related collection of data, and a <b>database management system (DBMS)</b> is the software that manages the storage, retrieval, updating and protection of that data against many concurrent users and failures (PostgreSQL, MySQL, SQLite, Oracle, MongoDB, ...).

@@ b1-1|body#3

@@ b1-1|body#4
<b>Concurrency:</b> two programs update one file at the same time and corrupt each other.
@@ b1-1|body#5
<b>Atomicity:</b> if a money transfer between two accounts is left half-done, money vanishes.
@@ b1-1|body#6

2. Three-level architecture and data independence
@@ b1-1|body#10
The ANSI/SPARC architecture sees data at three levels: the <b>external level (view)</b> for each user/application, the <b>conceptual (logical) level</b> that describes the whole structure (tables, constraints), and the <b>internal (physical) level</b> which is how data is stored on disk (pages, indexes). This separation gives two kinds of <b>data independence</b>: <i>physical independence</i> (changing indexes/file layout without changing the tables and queries) and <i>logical independence</i> (changing tables without breaking views). The foundation of "declarative" SQL is the same: you say <i>what</i> you want, not <i>how</i>.

1. The relational model
@@ b2-1|body#1
The relational model (Codd, 1970) sees data as a <b>relation</b>. If the attributes are $A_1,\dots,A_k$ with domains $D_1,\dots,D_k$, a relation is a subset of the Cartesian product $D_1\times\dots\times D_k$; that is, a <b>set</b> of tuples. Important consequences: the order of rows is meaningless; in the theoretical model there are no duplicate rows (SQL relaxes this and is a "bag"); and the order of columns is not intrinsic either. <b>Degree</b> = the number of columns, <b>cardinality</b> = the number of rows.
@@ b2-1|body#2
2. Keys
@@ b2-1|body#3
<b>Superkey:</b> a set of attributes whose value identifies every row uniquely.
@@ b2-1|body#4
<b>Candidate key:</b> a <i>minimal</i> superkey; removing any attribute destroys uniqueness.
@@ b2-1|body#5
<b>Primary key:</b> the chosen one among the candidate keys; it has no NULL. The others are <b>alternate keys</b> and are enforced with <code>UNIQUE</code>.
@@ b2-1|body#6
<b>Foreign key:</b> an attribute that references a candidate/primary key of another table and guarantees <b>referential integrity</b>.
@@ b2-1|body#7
A <b>surrogate key</b> like <code>id AUTO_INCREMENT/UUID</code> versus a <b>natural key</b> like a national ID number.

4. NULL and three-valued logic
@@ b2-1|body#14
<code>NULL</code> means "unknown/inapplicable value", not zero or an empty string. Comparing with NULL gives <b>UNKNOWN</b>: <code>NULL = NULL</code> is neither true nor false; to test you must write <code>IS NULL</code>. <code>WHERE</code> keeps only TRUE rows. The truth table: <code>TRUE AND UNKNOWN = UNKNOWN</code>, <code>FALSE AND UNKNOWN = FALSE</code>, <code>TRUE OR UNKNOWN = TRUE</code>. Note: <code>NOT IN (subquery)</code> returns no rows if the subquery contains NULL — a famous trap.

1. Aggregate functions and GROUP BY
@@ b3-2|body#1
<code>COUNT, SUM, AVG, MIN, MAX</code> summarize several rows into one value. <code>GROUP BY</code> splits the rows into groups with the same value of the grouping columns and computes the function in each group. <code>COUNT(*)</code> counts all rows but <code>COUNT(col)</code> does not count rows where that column is NULL. Aggregates ignore NULL (<code>AVG</code> is the mean of the non-NULL values).
@@ b3-2|body#2
filter on the aggregate result
@@ b3-2|body#3
<b>WHERE versus HAVING:</b> <code>WHERE</code> applies to rows <i>before</i> grouping and cannot take aggregates; <code>HAVING</code> applies to groups <i>after</i> grouping. The logical execution order of a SELECT (not the order of writing):
@@ b3-2|body#4
<code>FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT (and windows) → DISTINCT → ORDER BY → LIMIT</code>

What is the difference between <code>NOT IN</code> and <code>NOT EXISTS</code> when the subquery returns NULL?
@@ b3-2|ex:4:a#0
<code>x NOT IN (a, b, NULL)</code> is equivalent to <code>x&lt;&gt;a AND x&lt;&gt;b AND x&lt;&gt;NULL</code>; the last term is UNKNOWN so the whole expression is never TRUE and no row is returned. <code>NOT EXISTS</code> only tests whether a matching row exists and does not count NULL as a "match"; so it is safer.
