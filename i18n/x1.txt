One array, two worlds
@@ x1|body#1
In the data-structures lessons we saw that an array is a contiguous block of memory with $O(1)$ access. In linear algebra, vectors, matrices and tensors are mathematical objects with operations (multiplication, transpose). <b>The link:</b> libraries like NumPy, PyTorch and TensorFlow store every tensor as <b>one contiguous 1D array</b> and put a "multi-dimensional view" on it defined by two pieces of data: the <b>shape</b> (the dimensions) and the <b>strides</b> (how many elements to skip to move one unit along each dimension).

Why does it matter?
@@ x1|body#14

Why is traversing a row-major matrix with a "column first, then row" loop slower than "row first, then column"?
@@ x1|ex:3:a#0
In row-major layout the elements of a row are adjacent in memory. Traversing row by row makes the accesses contiguous (cache hits and prefetching). From the BST to the index
@@ x3|body#1
A database index is a <b>search tree</b> over the keys that points to <b>disk pages</b> instead of memory nodes. If we put a balanced binary BST on disk, every comparison reads a page: $\log_2 n$ accesses. For $n=10^8$ that is about 27 random I/Os (≈ 2.7 ms on an SSD) — far too many. If we make each node a whole page (8–16 KB with hundreds of keys), the fan-out $F$ rises and the height becomes $\log_F n$; the result is the <b>B-tree/B+tree</b>.
@@ x3|body#2
$h_{BST}=\lceil\log_2n\rceil$ versus $h_{B^+}=\lceil\log_F n\rceil$. For $F=200$ and $n=10^8$: $h\approx\lceil 8/2.3\rceil=4$. Most of the time the root and second level are in the buffer pool, so a point query may need only 1–2 real I/Os.

Node rules (capacity $m$ keys)
@@ x4|body#1
Leaf: at most $m$ keys; linked to the next leaf. Internal node: $k$ separator keys and $k+1$ children.
@@ x4|body#2
Search: in each internal node choose child $i$ with $key_{i-1}\le x<key_i$.
@@ x4|body#3
<b>Leaf split:</b> after an overflow ($m+1$ keys), the right half goes to a new leaf and the <i>smallest key of the new leaf</i> is copied up to the parent (the key stays in the leaf too).
@@ x4|body#4
<b>Internal-node split:</b> the middle key is <i>moved</i> to the parent (not repeated in the internal node).
@@ x4|body#5
If the root splits, a new root is created with one key and the height increases by 1. <b>All leaves are always at the same depth.</b>

Estimating orders of magnitude
@@ x5|body#1
A modern CPU performs about $10^8$–$10^9$ simple operations per second. Knowing $n$ and the complexity we can tell without running whether a program takes "seconds", "hours" or is "impossible". Rule: $n\le10^4$ means $O(n^2)$ is acceptable; $n\le10^6$ means $O(n\log n)$; $n\ge10^8$ means in practice only $O(n)$ or less (and that with I/O).
@@ x5|body#2

@@ x5|body#3
A few lessons for working with data
@@ x5|body#4
<b>Nested loops on big data:</b> comparing all pairs (like computing an $n\times n$ similarity matrix or brute-force nearest-neighbour search) for $n=10^6$ is $10^{12}$ operations. Remedies: approximate indexes (HNSW/IVF), sampling, blocking.
@@ x5|body#5
<b>Join:</b> a nested loop $O(nm)$ in a database is a disaster on large tables; a hash join is linear.
@@ x5|body#6
<b>Sort-based versus hash-based:</b> removing duplicates by sorting $O(n\log n)$ or by hashing $O(n)$.
@@ x5|body#7
<b>I/O dominates:</b> for data larger than memory the number of passes over the disk matters more than the CPU (external merge sort, MapReduce).
@@ x5|body#8
<b>Distribution and parallelism</b> reduce the constant, not the growth order: even 1000 machines do not make $O(n^2)$ practical for $n=10^{10}$.
@@ x5|body#9
<b class="t">The hidden-constants trap</b>Binary search on data on disk, if each step is an I/O, is slower than a sequential scan of small data. Always measure with a profiler.
